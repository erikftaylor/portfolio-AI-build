# References

A place to record design references that inform Design Lab — without letting them turn into direct imitation.

## Why capture references at all

It's easy to save a screenshot, like it, and then unconsciously rebuild it feature-for-feature. That produces a portfolio that looks like someone else's site instead of one that demonstrates Erik's own design judgment — the opposite of the point. Capturing the *underlying principle* separately from the *reference itself* is what keeps a reference useful without becoming a template.

## Format

For every reference, capture all five fields. A reference with only a screenshot and no analysis is not usable — throw it out or fill in the rest before it goes in.

```
### <short title>

REFERENCE
<link, screenshot description, or citation — where this came from>

WHAT I LIKE
<the specific, concrete thing that works — not "it looks clean," name the actual mechanism>

UNDERLYING PRINCIPLE
<the general design idea this is an instance of, stated so it could apply somewhere else entirely>

WHAT NOT TO COPY
<the specific surface choices that are tied to the source's own brand/content/context and should not transfer>

HOW IT MAY INFORM THIS PORTFOLIO
<which direction(s) this is relevant to, and how — reference a specific brief in /design-lab/directions/ if possible>
```

## Rule

References inform *principles*. Principles inform *decisions* (recorded in [`/design-lab/decisions/`](../decisions/README.md)). A reference should never be traceable 1:1 into a shipped component — if a reviewer could point at the reference and the shipped result and say "that's the same layout," the abstraction step got skipped.

## Where to file them

One entry per reference in this file, or split into per-direction files (`references/editorial.md`, etc.) if this file gets long. Keep whichever structure is easier to actually maintain — an unused reference file is worse than no reference file.
